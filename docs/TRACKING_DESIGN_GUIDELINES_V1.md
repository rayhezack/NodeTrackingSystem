# 埋点设计规范 V1（待业务校验）

## 核心结论

埋点设计必须从业务问题出发，以“事件可判定、参数可解释、口径可复现、信息可追溯”为最低标准。AI 只负责生成初稿，不得补造 PRD 中不存在的事实；分析师确认后才能写入需求单并提交评审。

## 1. 适用范围与依据

### 1.1 适用范围

- 当前 MVP：同时支持 App 与 Web 埋点设计；两端分别读取对应正式库并使用各自端别、处理方和参数适用性枚举。
- PRD 输入：飞书 `wiki/docx` 正文。
- 输出对象：埋点设计表单所需的事件与参数字段，以及字段内的“待人工确认”标记。
- 不包含：PDF、Sheet、图片 OCR；上述能力放在第二期。

### 1.2 归纳依据

- App 正式埋点库及当前埋点管理系统字段、状态流转和权限代码。
- 历史需求 `APP_REQ_LEGACY_RECVQZLFAQ4U8U`，包含 7 个事件与 12 条参数记录。
- 历史事件模式：`bg_remove_entry_expose`、`bg_remove_entry_click`、`bg_remove_result`、`bg_remove_downstream_click`、`signup_page_expose`、`sub_start_expose`、`createflow_form_submit`。
- 参考埋点表格的事件、事件说明、事件类型、上报时机、参数名、类型、定义、必传和枚举结构。

以上材料只能证明当前实践，不等于已经生效的公司制度；本文件标记为“待业务校验”的内容需由数据负责人确认后升级为正式版。

### 1.3 AI 上下文来源与优先级

- 事实源：当前需求单“需求链接”字段中的飞书 PRD 正文；生成时自动读取，不要求分析师再次粘贴。
- 约束源：与当前端（App/Web）一致的历史正式埋点 Base 库，用于事件复用、命名和参数口径参考。
- 冲突规则：PRD 决定本次业务事实，历史库约束设计方式；两者冲突时标记“待人工确认”，历史案例不得覆盖 PRD。
- 追溯要求：草稿保留 PRD 地址与版本；正式事件复用由分析师通过系统现有复用入口执行。

## 2. 标准工作流

1. 业务方提交需求名称、PRD、适用端、优先级和项目参与人。
2. AI 读取 PRD、当前需求上下文、正式事件库和历史高质量案例。
3. AI 生成版本化草稿，只输出埋点设计表单字段，并在无法确认的字段中标记“待人工确认”。
4. 数据分析师逐事件选择是否应用；系统不得自动覆盖已有草稿。
5. 分析师补齐“待人工确认”内容并检查事件、参数与分析目标。
6. 检查通过后，进入既有埋点评审、开发、验收和上线流程。

## 3. 事件设计规范

### 3.1 先定义业务问题

每个事件至少服务于以下一种分析用途：

- 规模：页面、组件或功能的曝光/使用人数与次数。
- 转化：曝光 → 点击 → 提交 → 成功等漏斗。
- 路径：入口、页面和下游动作之间的流转。
- 质量：任务成功率、失败率、失败原因和异常分布。
- 策略：不同入口、模板、场景或实验组的效果差异。

无法说明分析用途的事件不应生成。

### 3.2 事件保持原子性

- 一个事件只表示一个可以客观判断的动作或状态结果。
- 曝光、点击、提交、结果应拆成独立事件，不能用一个事件同时表达多个阶段。
- 同一动作在不同页面的业务含义不同且需分别决策时，应拆事件或增加明确的场景参数。
- 仅 UI 样式变化、没有分析决策价值的过程不埋点。

推荐的基础链路：

```text
entry_expose -> entry_click -> form_submit/task_start -> task_result -> downstream_click
```

### 3.3 `evt_id` 命名

- 使用小写 `snake_case`。
- 推荐结构：`业务对象/场景 + 动作或结果`，例如 `bg_remove_entry_click`。
- 常用动作后缀：`expose`、`click`、`submit`、`start`、`result`。
- 禁止拼音、无业务含义缩写、纯页面序号和同需求内重名。
- 正式事件复用时保留正式 `evt_id`；若业务语义已改变，应新建事件，不能借旧 ID 表达新口径。

### 3.4 事件中文名与事件定义

- 中文名采用“业务对象 + 动作/状态”，让产品、研发、分析师无需查看代码即可理解。
- 事件定义写清“谁在什么场景做了什么”，并说明事件代表的业务事实。
- 定义不能只重复中文名，也不能混入上报实现细节。

示例：

```text
事件中文名：去背景入口点击
事件定义：用户在创作入口点击“去背景”功能入口，用于衡量入口点击率和来源场景差异。
```

### 3.5 触发时机

触发时机必须同时回答：

- 触发主体：客户端、前端或服务端。
- 触发动作：曝光、点击、提交、任务结束等。
- 成功边界：完成渲染、请求发出、服务端受理还是任务成功。
- 失败边界：哪些失败会触发，哪些取消不触发。
- 去重要求：一次页面生命周期、一次点击、一次任务或一次请求只报一次。

禁止使用“用户操作时上报”“发生时上报”等不可执行描述。

### 3.6 曝光、点击和结果事件

- 曝光：明确可见性阈值、页面/组件生命周期和重复曝光规则；仅创建 DOM 或接口返回不等于曝光。
- 点击：在用户点击且动作被客户端接受时上报；需要区分位置时用明确参数，不复制多个语义相同事件。
- 提交：明确是在校验通过、请求发出还是服务端受理时上报。
- 结果：优先表达终态，至少区分 `success/fail`；失败原因使用条件必传参数。
- 取消：只有当取消本身具有决策价值时才作为结果或独立动作记录。

## 4. 参数设计规范

### 4.1 参数字段必须完整

每个参数必须填写：

| 字段 | 规范 |
|---|---|
| 参数名 | 小写 `snake_case`，在事件内唯一 |
| 数据类型 | `STRING`、`NUMBER`、`INTEGER`、`BOOL/BOOLEAN`、`ARRAY`、`OBJECT`；不能确定时标记 `UNKNOWN` |
| 参数定义 | 说明业务含义和统计口径，不能只翻译字段名 |
| 必传规则 | `必传`、`非必传`、`条件必传` |
| 条件说明 | 条件必传时必须写清触发条件 |
| 枚举/范围 | 列出所有已知合法取值；开放文本需说明格式或长度 |
| 默认值/示例 | 提供合法示例；不能用示例代替定义 |
| 适用端 | App 通用、仅 iOS、仅 Android或待确认 |

### 4.2 参数命名与复用

- 同一业务含义在不同事件中应使用同名、同类型、同口径参数。
- 名称应表达业务语义，例如 `failure_reason`、`enter_from`、`referrer_page_name`。
- 禁止 `type`、`status`、`value` 等脱离上下文后无法理解的泛化名称。
- 正式公共参数优先复用；不得为同一含义创造多个别名。

### 4.3 必传与条件必传

- 核心分析维度且触发时一定可获得：设为必传。
- 仅特定分支存在：设为条件必传，并写明条件。
- 示例：当 `task_result=fail` 时，`failure_reason` 条件必传。
- “非必传”不代表可以随意缺失；仍需说明何时可能为空。

### 4.4 枚举与范围

- 推荐格式：`value // 中文含义`，一行一个取值。
- 枚举值使用稳定英文标识，不直接使用可能变化的 UI 文案。
- PRD 未给出的枚举不得由 AI 自行补造，统一标记“待人工确认”。
- 结果类枚举必须互斥且尽量完备；无法完备时明确未知值处理规则。

### 4.5 来源和上下文参数

历史案例体现出以下有效模式：

- `enter_from`：进入当前功能的业务入口。
- `referrer_page_name`：前序页面。
- `referrer_widget_name`：前序组件或控件。
- `event_page`：事件发生页面。
- `click_result`：点击后的可判定结果。
- `failure_reason`：失败结果下的原因，通常为条件必传。

这些名称只能作为结构参考；是否使用及其枚举必须由当前 PRD 或正式参数库支持。

## 5. 正式事件复用规范

- AI 初稿当前不自动执行正式事件复用，只把同端正式事件和参数作为命名、类型、必传及枚举口径参考。
- 分析师确认需要复用时，通过需求单“复用已有事件”入口选择真实正式事件，系统负责导入参数。
- 语义、触发边界和核心口径完全一致时可以复用。
- 复用已有事件时，归档只允许追加新参数；复用已有事件且复用已有参数时，归档只允许追加新枚举值，正式事件、正式参数和已有枚举定义的其他字段保持不变。
- 事件语义、统计主体、触发边界或核心参数口径改变时必须新建事件。
- 同一需求内禁止重复 `evt_id`；跨需求复用同一正式事件允许。

## 6. 信息不足与 AI 防幻觉规则

- AI 先生成能够从 PRD 和正式库确认的部分。
- 无法确认的版本号、枚举、触发边界、研发实现、公共属性等写“待人工确认”。
- 每个不确定项必须进入 `uncertainties` 或分析师问题列表，不能藏在正文中。
- 每个事件至少返回一条 PRD 证据；证据应是定位线索或短摘要，不大段复制原文。
- PRD 存在冲突时同时展示冲突内容，由分析师决定，不擅自选择其中一个版本。
- 历史案例只用于学习结构和命名，不能把历史业务事实迁移到新需求。

## 7. 评审门禁

### 7.1 事件级检查

- 是否明确支撑业务指标或决策？
- 是否与其他事件重复或可以复用正式事件？
- 事件粒度是否单一？曝光、点击、提交、结果是否被错误合并？
- 定义和触发时机是否足够让研发无歧义实现？
- 成功、失败、取消、重复触发的边界是否明确？
- `evt_id`、中文名、端、处理方、版本和变更类型是否完整？

### 7.2 参数级检查

- 参数是否真正用于分组、过滤、归因或诊断？
- 类型、定义、必传规则、条件、枚举和示例是否自洽？
- 枚举是否互斥、稳定、覆盖已知业务分支？
- 失败原因、来源和场景参数是否在正确条件下必传？
- 是否重复创建了正式库已有的公共参数？
- 是否仍有未处理的“待人工确认”？

### 7.3 提交评审前门禁

以下任一条件存在时不得提交评审：

- 缺少 PRD 或 PRD 无读取权限。
- 事件没有分析用途、事件定义或可执行触发时机。
- 参数缺少类型、定义或必传规则。
- 枚举由 AI 猜测且未得到业务确认。
- PRD 冲突尚未解决。
- 正式事件复用来源或修改内容未展示。

## 8. 待数据负责人校验

- `evt_id` 是否统一采用“业务对象 + 动作”结构，还是按产品域增加固定前缀。
- App 公共参数的正式清单、自动注入边界及是否需要在事件设计中重复声明。
- 曝光事件的统一可见性阈值、停留时间和去重周期。
- `BOOL` 与 `BOOLEAN` 是否收敛为单一类型。
- 版本、最低版本和优先级的默认策略；AI 当前不得自行补造。
- `处理方` 在客户端、服务端和双端协同时的最终枚举与责任边界。
- 参数枚举的正式文本格式及未知值兜底规范。

完成上述校验后，建议将本文件升级为正式规范，并作为 AI 埋点 Skill 的固定知识文件与评审清单。
