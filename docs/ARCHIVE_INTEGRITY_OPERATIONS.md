# 归档完整性与恢复

## 数据契约

- 正式枚举按端、evt_id、参数名、枚举原值精确去重，保留大小写。既有字典关联值不会因参数单元格缺少该值而丢失。
- 枚举字典是结构化值来源；“枚举/取值范围”为兼容投影，同时接受尚未迁移、可明确解析的历史值作为增量。无法判断的说明文字拒绝自动入库。
- 原有正式事件与参数定义不可覆盖。重复参数（含正式/待治理冲突）必须先处理，不按查询顺序任选一条。
- 创建、更新返回数量和 ID、分页完整性都必须通过校验。同步完成后才更新整份需求归档状态。

## Pollo Cloud 并发与幂等

所有经 Pollo Cloud `/api/tracking/records`、`params`、`permissions` 的写入和 AI 草稿应用，共用 D1 `tracking_base_writer` 单写门禁。查询与 AI 生成不受影响；并发写返回 409，用户稍后重试。该范围刻意覆盖跨需求写同一参数，避免只锁需求 ID 的漏洞。

`tracking_base_keys` 为正式事件、正式参数、枚举行记录精确唯一键和创建后的 Base ID。Base 查询可见性延迟时，不会因“读不到”而重复创建。写入结果无法确认的键不会自动撤销。

`tracking_base_writes` 记录运行、成功、校验拒绝或 `needs_reconciliation`。发生未知写入错误/任务中断时，保留单写门禁，不使用过期租约自动接管，因为旧的 Feishu HTTP 请求可能仍提交。正常成功或 4xx 校验失败才自动释放。

这些保护作用于 Pollo Cloud 应用入口，不能约束人在 Base 中直接编辑、SUNWEN CLI 或另一套妙搭/Nest 服务直接写同一批表。生产应保持单一写入口，维护时也必须持有门禁。

## 人工恢复未确认写入

1. 用 `pollocloud db execute --name app-tracking-management` 查询 `tracking_base_writer` 的 owner、started_at 及对应 `tracking_base_writes` 状态。不要直接清空全部门禁或唯一键表。
2. 确认原任务已停止。用 SUNWEN CLI 完整分页读取涉及事件、参数及枚举，核对唯一键、参数关联、状态和最后写入。保留快照。
3. 如果未确认的 `tracking_base_keys` 键已经有 Base 记录，按 instance、identity、owner 精确补回 record_id；存在重复或冲突时先治理。
4. 只有确认没有任何记录且原请求不会再提交，才按 instance、identity、owner 精确删除该未确认 claim，允许下次重试。
5. 完成差异补齐后，将作业标为 reconciled；使用 `DELETE ... WHERE id='global' AND owner=<核实的owner>` 释放门禁。重新执行归档，再读回验收。

禁止为了恢复操作而绕过锁强行并发归档，或清空唯一键记录后盲目重试。

## 存量清理顺序

先写前快照、生成变更清单，再执行：迁移引用 → 存档待治理副本 → 删除重复副本 → 修正草稿/正式状态 → 补齐缺失参数 → 补登记可明确识别的枚举及关联 → 重建兼容投影。每批最多 200 条，写后完整读回。

自由文本、URL、ID 描述、未知语义和不明确的范围说明不推断成枚举。清理它们需要保留原始文本，并明确列为待业务确认，不用测试数据覆盖生产记录。
