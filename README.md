# Pollo AI 埋点项目管理系统

**核心结论：这是一个基于飞书妙搭 + 多维表格 Base 的埋点需求管理系统，用来把“提需求、做埋点设计、评审、开发、验收、上线、归档、查询”串成一条可追踪的闭环流程。**

线上地址：[https://bcn0tgplxp2e.aiforce.cloud/app/app_17apvbcusvs](https://bcn0tgplxp2e.aiforce.cloud/app/app_17apvbcusvs)

## 适用场景

- **业务方/产品提需求：** 普通公司内部同事可以提交埋点需求；创建者自动成为需求提出人，数据负责人默认孙文，埋点校验人默认孙文和刘桥，研发负责人按需求指定。
- **数据分析师做设计：** 数据负责人可以在一个需求内维护多个埋点事件、参数、枚举值、UI 图和触发口径。
- **研发查阅与开发：** 研发负责人可以直接查看埋点设计详情和全部参数说明，支持复制参数说明用于开发对接。
- **上线后归档查询：** 归档成功的埋点事件和参数会同步到正式查询库，供后续查询和复用。

## 核心业务流程

```mermaid
flowchart LR
  A["埋点提需 / 需求录入"] --> B["埋点设计"]
  B --> C["埋点评审"]
  C --> D["埋点开发"]
  D --> E["埋点校验 / 数据验收"]
  E --> F["埋点上线 / 上线监控"]
  F --> G["归档 / 正式查询库"]
```

- **需求录入：** 填写需求名称、背景、使用场景、端、优先级和项目参与人。
- **埋点设计：** 在同一需求 ID 下维护一个或多个埋点事件，并编辑事件定义、触发时机、UI 图、版本、变更类型和参数明细。
- **埋点评审：** 提交评审按需求单粒度推进，同一需求下所有埋点事件一起进入评审。
- **埋点开发：** 研发负责人查看设计交付面板，确认开发状态。
- **数据验收：** DS 或数据负责人记录验收状态、证据和验收时间。
- **上线监控：** 维护发布状态、门禁状态、上线监控结论。
- **归档：** 已上线事件和参数同步到正式查询库；仅校验类事件不修改正式库。

## 主要功能模块

### 埋点工作台

- **我的待办：** 按需求单展示待办，不再按单个 evt_id 拆散；被指定为需求提出人、数据负责人、研发负责人或埋点校验人时，会看到进行中的需求单。
- **需求列表：** 按需求 ID 聚合多个埋点事件，支持按关键词、阶段、优先级、平台筛选。
- **阶段统计：** 按工作流节点统计当前需求进展。
- **新增需求：** 业务方可创建需求单，需求链接可选，验收字段不在提需阶段强制填写。

### 埋点详情页

- **顶部流程条：** 展示 7 个工作流节点及完成状态。
- **左侧阶段导航：** 按需求录入、埋点设计、评审、开发、数据验收、上线监控、归档组织表单。
- **同需求多事件：** 一个需求 ID 下可新增多个埋点事件；切换事件时使用已加载缓存，不重复刷新整页。
- **复用已有事件：** 支持从正式查询库选择已有事件，并只导入需要修改的参数。
- **参数设计：** 支持新增、编辑、删除、批量删除参数；参数版本默认继承事件版本；参数适用端已去重。
- **研发交付视图：** 在开发阶段可直接查看事件和参数明细，降低研发逐个点击参数的成本。
- **UI 图预览：** 支持上传后的 UI 图预览，兼容文件名、存储路径和临时链接解析。

### 正式查询库

- **事件查询：** 查询已上线/归档的埋点事件。
- **参数查询：** 查看正式参数、含义、枚举值、必传规则、适用端等。
- **归档同步：** 归档时将设计事件和设计参数增量同步到正式查询库，同时回传数据负责人、研发负责人、埋点校验人、稳定归档时间、优先级、最低版本、处理方和源事件记录 ID 等追溯字段。
- **复用基础：** 埋点设计阶段可基于正式库事件追加参数或枚举值，最终归档时 append 到正式库，而不是覆盖历史值。

### 权限配置

- **管理员：** 管理权限配置，拥有全流程管理能力。
- **普通用户：** 可创建需求和查看自己参与的需求。
- **项目角色：** 需求内指定的需求提出人、数据负责人、研发负责人、埋点校验人拥有对应流程节点的阅读和编辑权限；旧“需求录入人”字段仅为 Base 兼容字段并自动镜像提出人，不再作为独立业务角色展示。
- **研发负责人特殊权限：** 被指定后可编辑从需求录入到埋点开发阶段的关键内容，方便研发负责人分配和跟进人力。

### 节点流转通知

- **触发时机：** 需求从一个节点完成并流转到下一个节点时，系统会按下一节点责任人发送飞书机器人私信。
- **通知对象：** 节点通知按责任人发送；上线监控完成后默认通知需求提出人、数据负责人、研发负责人和埋点校验人，并按人员去重。
- **身份策略：** 使用深圳九瓴科技有限公司通讯录核验的邮箱，由机器人应用调用 `contact/v3/users/batch_get_id` 解析租户级 `user_id` 后投递。通知链路不再直接使用 `open_id`，也不把妙搭数字人员 ID 当作飞书 `user_id`。
- **多人负责人：** 多个责任人会逐个独立发送；单人失败不会阻断其他责任人，前端会区分“全部送达、部分送达、全部失败”。
- **Bot 可用范围：** 妙搭应用运行时可见范围与飞书开放平台机器人可用范围是两层配置；若飞书返回 `Bot has NO availability to this user`，需要在开放平台把机器人应用的可用范围加入该用户或所在部门，并重新发布应用版本。
- **异常反馈：** 前端完成节点时会展示通知成功、跳过或失败原因，便于定位权限、身份或机器人可见性问题。
- **归档回跳：** 完成归档后自动返回埋点工作台，避免继续停留在已结束的需求详情页。

## 关键数据模型

| 层级 | 说明 | 关键字段 |
|---|---|---|
| 需求单 | 工作台展示与待办聚合的最小业务单元 | `需求ID`、`需求名称`、`流程阶段`、项目参与人 |
| 埋点事件 | 一个需求下可以包含多个事件 | `evt_id`、`事件中文名`、`事件定义`、`触发时机`、`变更类型` |
| 设计参数 | 设计阶段维护的参数明细 | `设计参数主键`、`参数名`、`数据类型`、`必传规则`、`枚举/取值范围` |
| 正式事件 | 归档后进入正式查询库的事件 | `evt_id`、`事件中文名`、`状态`、项目负责人、`稳定归档时间`、`参数明细入口` |
| 正式参数 | 归档后进入正式查询库的参数 | `参数主键`、`参数名`、`枚举/取值范围`、`参数状态` |

## 发布流程

**发布前必须确认本地提交已 push 到远端 `sprint/default`，因为妙搭 release 读取的是远端分支，不是本地工作区。**

推荐流程：

```bash
git status --short
git rev-parse --short HEAD
git push origin sprint/default
/Users/ray/.codex/skills/feishu-sunwen-cli/scripts/sunwen-lark-cli apps +release-create --as user --app-id app_17apvbcusvs --branch sprint/default
```

发布创建后使用 release ID 查询：

```bash
/Users/ray/.codex/skills/feishu-sunwen-cli/scripts/sunwen-lark-cli apps +release-get --as user --app-id app_17apvbcusvs --release-id <release_id>
```

只有当返回 `status=finished` 且 `commit_id` 对应本次提交时，才能确认本轮发布完成。

## 维护原则

- **需求粒度优先：** 工作台、待办、提交评审等流程动作应优先按需求单聚合，避免用户误以为只处理了某个 evt_id。
- **事件粒度设计：** 事件定义、触发时机、UI 图和参数仍保持事件粒度，避免多个事件互相污染。
- **正式库增量合并：** 复用已有事件时，只维护本次需要变更的参数或枚举；归档时在正式库基础上 append/merge，不覆盖历史。
- **Base 字段契约收敛：** 前端表单不出现的字段，不应在当前节点强制必填；日期、链接、附件、人员、多选字段必须按 Base 类型写入。
- **性能优先减少整页刷新：** 需求详情、同需求事件和参数列表应尽量本地缓存与局部更新，保存或节点完成时再按需回读 Base。
- **通知身份统一在机器人应用内解析：** 工作流通知优先从 Base 人员快照取得邮箱，再通过机器人 `tenant_access_token` 查询租户级 `user_id`；禁止直接复用其他应用生成的 `open_id`。
